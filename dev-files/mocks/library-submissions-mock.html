Notes — Submissions

  1. Review work floats to the top instead of hiding behind a checkbox. “Needs review only” asked the DJ to remember there was a queue and then opt into it. Sorting anything with open review work above the chronological list means the queue is simply the first thing on the page, and the status dropdown still narrows to one state when that is what you want. Two group labels keep the non-chronological order from looking like a bug.
  2. The tile replaces the artwork slot. Submissions have no artwork, but the left rail is where the eye lands, so the tile carries the status tone (green committed, amber review, blue processing, red failed, neutral dismissed). Status becomes scannable down the column before any text is read.
  3. Counts become columns, not a run-on caption. Today the row ends with “1 committed · 2 need review · 1 failed” and a Review badge and a timestamp in one wrapping line. Committed and Review get their own centered numeric columns with the crate’s em-dash-when-zero rule, so rows line up.
  4. The second line answers “what happened to this note”. Proposal count plus the one fact that matters for that state: unmatched tracks while reviewing, model and extraction version once committed, the error string when it failed. All of it is already on the list payload.
  5. Preview drops to one line. Two-line clamping made every row a different height. One line at 13.5px with the second line doing the work is denser and still readable.
  6. Ships with no API change. Status, proposalCounts, extractionError, model, and extractionVersion all already come back from GET /submissions. “2 tracks unmatched” is the only line that would need review-reason counts — it can fall back to the proposal count. The pinned group is a client-side partition on proposalCounts.needsReview > 0, so it works with the existing ?needsReview=1 query the masthead link already uses.
